## ADDED Requirements

### Requirement: SIP SDP is parsed by m-line position

The gateway MUST read the primary audio endpoint only from the first `m=audio` line and the primary video endpoint only from the first `m=video` line of a SIP SDP body. A later `m=video` line MUST NOT change the primary video RTP destination, payload type, direction or active state of the session.

#### Scenario: Second video m-line does not move the camera destination

- **WHEN** an in-dialog re-INVITE or UPDATE carries `m=audio`, a first `m=video` on port 20002 and a second `m=video` on port 20006
- **THEN** the session's primary video RTP destination MUST be port 20002
- **AND** the second `m=video` MUST be evaluated only as the auxiliary stream

#### Scenario: Mid-call validation reports each video m-line separately

- **WHEN** mid-call SDP validation runs on an offer whose first `m=video` is `sendrecv` and whose second `m=video` has port 0
- **THEN** the primary video MUST be reported as active
- **AND** the offer MUST NOT be classified as "video removed"

### Requirement: SIP answers mirror the offer's m-line count and order

The gateway MUST answer a SIP SDP offer with exactly as many `m=` lines as the offer contains, in the same order. An offered m-line the gateway does not use MUST be answered with port 0 and the offered media type and transport.

#### Scenario: Unused extra video m-line is declined in place

- **WHEN** an inbound re-INVITE offers `m=audio`, `m=video` and a second `m=video`, and the gateway does not accept the second video stream
- **THEN** the 200 OK SDP MUST contain three `m=` lines in the same order
- **AND** the third MUST be `m=video 0` with the offered transport profile
- **AND** the first two MUST describe the session's existing audio and video endpoints

#### Scenario: Unknown media type is declined in place

- **WHEN** an inbound offer contains an `m=` line of a media type other than audio or video
- **THEN** the answer MUST contain a matching `m=` line with port 0 at the same position

### Requirement: SDP layout follows the latest offer/answer exchange

The gateway MUST generate every SIP SDP for a dialog from a per-session slot table that reflects the most recent completed offer/answer exchange. Once an auxiliary video slot has been negotiated, every SDP the gateway originates for that dialog MUST include it, with port 0 while it is closed. When the peer sends an offer with fewer m-lines than the current table, the gateway MUST answer with the offered count and reduce the table to match.

#### Scenario: Hold after a closed screen share keeps the m-line

- **WHEN** a session negotiated an auxiliary video slot, closed it, and the client then sends `hold`
- **THEN** the hold re-INVITE MUST contain three `m=` lines
- **AND** the auxiliary m-line MUST have port 0
- **AND** the audio and primary video m-lines MUST carry the hold direction

#### Scenario: Peer shrinks the SDP

- **WHEN** the slot table holds audio, primary video and auxiliary video, and the peer sends a re-INVITE with only `m=audio` and one `m=video`
- **THEN** the gateway MUST answer with two `m=` lines
- **AND** the gateway MUST close any open auxiliary stream for that session

### Requirement: Calls without an auxiliary stream keep their SDP

For a session that has never negotiated an auxiliary video slot, SIP SDP offers and answers generated by the gateway MUST be byte-identical to those generated before this change for the same inputs.

#### Scenario: Initial INVITE is unchanged

- **WHEN** the gateway builds the SDP for an outbound INVITE or the answer to an inbound INVITE
- **THEN** the body MUST contain one `m=audio` and at most one `m=video`, with the same lines and ordering as before this change
