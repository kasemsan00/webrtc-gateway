## Purpose

Define the canonical brand-neutral identity of the WebRTC-SIP Gateway across source, runtime, distribution, protocol-visible metadata, operations UI, and compatibility rollout.

## ADDED Requirements

### Requirement: Canonical gateway identity

The system SHALL use `WebRTC-SIP Gateway` as its canonical human-readable product name and `webrtc-sip-gateway` as its canonical machine-readable repository, backend runtime, and distribution identifier. The operations frontend SHALL use `WebRTC-SIP Gateway Console` as its human-readable name.

#### Scenario: Operator inspects a current release

- **WHEN** an operator reads current product documentation, inspects workspace metadata, or checks the running gateway process and primary image
- **THEN** those surfaces identify the system as `WebRTC-SIP Gateway` or `webrtc-sip-gateway` according to human-readable or machine-readable context and do not present `K2` as the active product brand

#### Scenario: Operator inspects the console

- **WHEN** an operator opens or deploys the operations frontend
- **THEN** it is identified as `WebRTC-SIP Gateway Console` and its primary distribution artifact uses the `webrtc-sip-gateway-console` identity

### Requirement: Runtime and distribution names are coherent

The gateway build, container entrypoint, supervisor, health check, log discovery, Compose profile, and published primary images SHALL agree on the canonical runtime and distribution names within one release.

#### Scenario: Split image starts

- **WHEN** the canonical split gateway image starts successfully
- **THEN** its entrypoint launches the `webrtc-sip-gateway` binary, its health check verifies that process, and its log API discovers files using the canonical log prefix

#### Scenario: Unified image starts

- **WHEN** the canonical unified image starts successfully
- **THEN** the stack supervisor and health check recognize the canonical gateway process while preserving the existing gateway/frontend readiness semantics

### Requirement: Temporary branding is absent from active maintained surfaces

Active source, UI text, runtime identifiers, build/deploy scripts, current normative documentation, and maintained consumer references SHALL NOT use `K2 Gateway`, `K2 WebRTC Gateway`, `k2-gateway`, `k2-frontend`, or `k2-stack` as the current product identity. Historical and migration references MAY retain an old name when their context explicitly requires it.

#### Scenario: Branding scan runs

- **WHEN** the repository temporary-brand scan evaluates active maintained files
- **THEN** it fails for an unapproved temporary-brand occurrence and reports the file and matched identity

#### Scenario: Historical or compatibility reference is retained

- **WHEN** a historical artifact or migration instruction must name an old identity
- **THEN** the occurrence is covered by an explicit documented exception and cannot silently authorize unrelated active branding

### Requirement: Go module rename is behavior-neutral

The backend SHALL use `webrtc-sip-gateway` as its Go module and first-party import prefix without moving packages or changing runtime call, signaling, media, persistence, authentication, push, or translation behavior.

#### Scenario: Backend is built after the rename

- **WHEN** the gateway and database-bootstrap commands are built and tested
- **THEN** all first-party imports resolve through `webrtc-sip-gateway`, both commands build successfully, and the existing Go test suite passes without a protocol behavior change

### Requirement: SIP product identity is brand-neutral

SIP requests generated by the gateway that include a gateway product token in `User-Agent` SHALL use `WebRTC-SIP-Gateway` instead of a `K2` product token while preserving the existing request method, header validity, and version semantics.

#### Scenario: Gateway sends SIP registration or call request

- **WHEN** the gateway emits a SIP request on a path that sets its product `User-Agent`
- **THEN** the header contains the canonical `WebRTC-SIP-Gateway` product token and contains no `K2-Gateway` token

### Requirement: Wire and data contracts remain unchanged

The identity migration SHALL NOT rename or remove existing WebSocket message types or fields, REST/SSE paths, environment variable names that do not contain temporary branding, database schema objects, SIP call-state mappings, or media capabilities.

#### Scenario: Existing client uses the gateway protocol

- **WHEN** a client built against the pre-rename WebSocket and REST contract connects to a reachable post-rename endpoint with otherwise valid configuration
- **THEN** its messages and API calls are processed without requiring a product-name field or protocol payload change

#### Scenario: Existing database is reused

- **WHEN** a post-rename gateway starts with an existing valid `DB_DSN`
- **THEN** it uses the existing database, role, schema, and data without requiring an infrastructure-name or schema migration solely for the product rename

### Requirement: Bootstrap locking remains compatible across releases

The product rename SHALL preserve the existing PostgreSQL bootstrap advisory-lock numeric value so old-name and canonical-name release images targeting the same database serialize bootstrap operations on the same lock.

#### Scenario: Old and new bootstrap images overlap

- **WHEN** a pre-rename bootstrap process and a post-rename bootstrap process run concurrently against the same database
- **THEN** they contend on the same advisory lock rather than classifying or migrating the database concurrently

### Requirement: Frontend persisted state migrates safely

The console SHALL migrate valid active browser state from legacy `k2-*` storage keys to canonical namespaced keys once, SHALL prefer an already present canonical value, and SHALL remove a migrated legacy key.

#### Scenario: Only a valid legacy value exists

- **WHEN** the console loads after upgrade with a valid supported value under a legacy key and no canonical value
- **THEN** it copies the value to the canonical key, removes the legacy key, and preserves the operator's effective setting or session state

#### Scenario: Both canonical and legacy values exist

- **WHEN** the console loads with values under both key generations
- **THEN** it uses the canonical value and removes or ignores the legacy value without overwriting the canonical state

#### Scenario: Legacy value is invalid

- **WHEN** the console encounters malformed or unsupported data under a legacy key
- **THEN** it does not promote that data and follows the existing safe default or logged-out behavior

### Requirement: External aliases support controlled migration

Where project-controlled released images or public endpoints use old product names, operators SHALL have a documented compatibility path that keeps the old reference mapped to the canonical service during the supported migration window. Retirement SHALL be an explicit rollout decision based on migrated consumers, not an automatic consequence of the source rename.

#### Scenario: Older deployed client uses the legacy hostname

- **WHEN** a supported older client connects through the retained legacy DNS/TLS name during the compatibility window
- **THEN** it reaches the same compatible gateway service without a WebSocket contract change

#### Scenario: Deployment still uses an old image name

- **WHEN** supported deployment automation pulls a retained compatibility image tag during the compatibility window
- **THEN** the tag resolves to the documented canonical release digest or a supported rollback artifact

#### Scenario: Compatibility alias is retired

- **WHEN** operators verify that supported clients and deployment automation have migrated and approve the end of the compatibility window
- **THEN** the old alias may be removed independently of application source and database state
